# Vibe Evals 评分表单填写

## Overview

读 vibe-evals-scoring 的反馈报告 + rubrics-{X}.json + 题包材料，按 V2.1 人评标准产单文件多模型评分表单（`Vibe Evals评测材料/{题}-评分表单.md`）。机器预填建议值，全部标注“待人工确认”，最终以人工拍板为准。

## 通用骨架

以下三块为技能族共用骨架，本技能全文生效（标题层级已按本文件调整）：

### Phase 0: 题包探测（MANDATORY，任何材料收集前执行）

给定用户提供的题包根路径（如 `.../双曲空间的推箱子游戏-0816`），探测以下内容并向用户汇报，缺关键材料时**停下来问参数**，不猜：

1. **轮次记录目录**：`{题}轮次记录/`，内含：
   - `prompt.md` — 题目各轮 prompt（MANDATORY，缺则停）
   - rubrics 基线判定（按优先级）：`合并rubrics*.json` → 无则 `rubrics*.json` → 再 `原rubrics*.json`（MANDATORY，全无则停）
   - `{X}模型对话记录.json` — CodeBuddy 导出（每个模型一个，命名 `{X}模型对话记录.json`）
   - `记录.txt` — 评测人人工记录（可选，存在时其内容为**权威人工意见**）
   - `R1/`、`R2/`… 每轮每模型快照子目录（`R1/{X}/{题}-{X}/...`）
2. **模型输出目录**：`{题}-模型输出/`，每个子目录 = 一个模型（模型标识 = 子目录名），自动探测模型列表与模型数 N（支持任意 N）
3. **上批次分析**：上一批次目录中的《对每条rubric的理解.md》（可选；存在则复制并过目）。上一批次目录由用户提供（通常为题包同级的上批次目录）；复制到本批输出目录供口径背景参考（可选，本技能 Phase 1 不直接消费）。
4. **字段解释**：资料包 `rubrics说明.xlsx`（可选；存在则读取字段语义）
5. **输出目录**：用户指定（无指定则询问）；**若输出目录已有同名金标准产物，必须换新目录，绝不覆盖**

探测完成后输出「探测结果」表（每个材料：路径 / 状态 / 用途），让用户确认后再进入 Phase 1。

### MANDATORY 纪律（贯穿全流程）

1. **主会话不读模型源码**——本技能通常只消费上游报告、已评分 JSON、对话记录和人工记录；若确需补充模型源码证据，使用 Codex `spawn_agent` 子智能体取证，并用 `wait_agent` 等待结构化回报；回报到达前不得继续评分或交稿；
2. **打分依据必须 file:line 或实测结果**——任何上游 0/1 判定或本技能建议分依据必须引用具体文件行号、实测输出或明确的上游证据，不允许“看起来像是实现了”；
3. **机器不擅自裁定判分口径**——遇到需人拍板的判分问题，产出“待裁定项”（附证据+建议口径）供人工裁定，不自行定论；
4. **兜底 0 分规则**：无输出产物 / 几乎未实现 prompt 重要实现 → 该模型总体 0 分（写进报告，不逐条打分）；
5. **0/1 二值、每条 1 分、无权重**（Must have / Nice to have 仅作元数据，不参与加权）；
6. **“未经纠正时”语义** = 以模型当轮自主产出为准（未经评测方纠正即正确才得分）；
7. **不碰原文件**：新 rubric 写新文件；原 rubrics 与金标准产物永不修改，仅本技能自产文件（`Vibe Evals评测材料/{题}-评分表单.md`）可写；
8. **Python 环境**：Windows 下 `python` 不可用时用 `py` 启动器（`py -c "..."`），绝不因此中断。

### 交稿前检查（全部通过才交稿）

- [ ] （技能专属检查项，见文末）
- [ ] 输出文件齐全，路径与命名符合模板
- [ ] 所有分数/证据交叉一致（md 与 json 数字一致）
- [ ] 无未处理的待裁定项

> 本技能的专属检查项见文末「交稿前检查」一节。

> 口径说明：纪律第 5 条（0/1 二值、每条 1 分、无权重）适用于上游 rubric 打分（rubrics-{X}.json 口径）；本技能产出 0-4、0.5 步长的人评表单，不适用二值纪律；纪律第 2 条的证据要求（file:line/实测）仍适用于每个建议分的打分依据。

## 前置检查：上游产物（Phase 1 之前）

执行顺序：题包探测 → 本前置检查 → Phase 1 材料通读 → Phase 2 机器预填。

检查输出目录内是否已有 vibe-evals-scoring 的产物：`反馈报告.md` + 每模型 `rubrics-{X}.json`（二者是本技能的数据源）。缺失则提示先跑 vibe-evals-scoring，不降级硬填；仅有原始模型代码、prompt 或未裁定的预打分都不满足前置条件。

## Phase 1: 材料通读

1. **反馈报告.md**：Rank（名次与并列关系）、4W1H（各模型问题归纳）、差异总表（拉开分差的条目）、判分口径（裁定项最终口径）；
2. **rubrics-{X}.json**（每模型一份）：逐条读 `score` / `reason`（reason 为打分人风格的证据句，Phase 2 维度映射时直接引用）；
3. **题包对话记录**（`{X}模型对话记录.json`）：重点看**首轮提问质量**——该模型首轮是否向评测方提问、问了什么，这是 R1 需求澄清维度的直接证据；
4. **记录.txt**（若有）：人工实测/排版意见（S1 视觉维度证据之一），内容为权威人工意见，引用时标注来源。

## Phase 2: 机器预填

按 [`templates/评分表单模板.md`](templates/评分表单模板.md) 产出 `Vibe Evals评测材料/{题}-评分表单.md`（单文件多模型），全部为机器建议值，**最终以人工拍板为准**。

**题目级共享节：**

- **模型排序**：档位制（1 = 最好，可并列），**排序与反馈报告 Rank 严格一致**，不自行重排；N=1 时仍保留“模型排序”节，档位为 1，并注明“单模型，无同场比较/无排序”；
- **并列一致性**：同一档位的并列模型使用相同总体印象建议分；不同档位的总体印象建议分不得倒序；
- **排序理由 / 洞察**：按下节「排序理由与洞察速记风格」写作（白话叙事：从最好到最差逐模型一句；洞察一句话一条共性规律）；
- **难点和思路**：按下节「排序理由与洞察速记风格」写作（题目难点 = 现象 + 本批真实案例；考察点/出题思路 = 白话说明出题意图与权重）；

**每模型节（顺序固定）：**

1. **总体印象分**（0-4，0.5 步长）：与排序严格一致；
2. **通用维度**：G1 指令遵循 / G2 功能交付 / G3 收敛效率；
3. **适用性门控维度** S1/A1/R1：
   - S1 视觉：前端题适用；
   - R1 需求澄清：模糊需求型题目适用——按本地 V2.1 口径，以首轮对话是否提问作为可评分门槛；首轮未提问则标 N/A 并注明“首轮未提问”，不把未提问换算成低分；
   - A1 架构：原则上后端题适用；但本地 V2.1 当前政策为“目前没有后端题暂不考虑”，因此在该政策更新前统一标 N/A，并注明政策依据；
   - **不适用一律标 N/A 并注明判定依据**，删除该维度的数字建议值与 0–4 勾选栏，不硬打分；
4. **文字反馈三块**：Pros / Cons / Style；每个适用维度的分数依据必须写进 Pros/Cons，且同一维度的数字分数在两块合计只写一次；**写法遵守下节「文字反馈速记风格」（用户定稿规范）**；
5. **Vibe 标签候选**：从 [`templates/V2.1标签库.md`](templates/V2.1标签库.md) 预选勾选（**有必要的都勾，可多选**，只勾有突出依据的标签，没有不硬贴）。

**文字反馈速记风格（2026-08-19 用户定稿；2026-08-21 一轮融合人工手写样例、二轮按子代理对比分析修订、三轮去编号化对外可读性修订、四轮补充落盘前自查清单、五轮 Pros 贴维度+不硬写（2026-08-22）；适用 Pros/Cons/Style 三块，标签节不适用）：**

文字反馈读起来像**真人评审的评分笔记**——"维度 + 分数 + 可观察事实"的流水账，按"首轮 → 调试过程 → 遗留问题"时间线叙事，带口语评价，只列现象不展开归因、不堆形容词、不写模板腔、不做总结升华。

- **维度标签与块内合并**：Pros 和 Cons 分别检查；同一块内同一维度标签最多出现一次，同维度的多个事实合并成一条。相同标签允许在 Pros 和 Cons 各出现一次，这不算重复。
- **只用单一维度标签**：标签只能完整使用 `【指令与约束遵循】`、`【功能交付完整性】`、`【任务收敛效率】`、`【视觉审美】`、`【需求理解与澄清】`、`【架构合理性】` 中适用且已评分的维度。禁止 `【A/B】`、`【A／B】`、`【A+B】`、`【A与B】` 等混合标签，也不使用 `【其他】`；跨维度事实拆到各自维度下。
- **每个标签只写一次分数**：以单个模型的 Pros 与 Cons 合集为范围，每个出现的维度标签必须且只能出现一次 `给了X分`，且 X 与该维度建议分一致。标签只在 Pros 出现时，由 Pros 写分；只在 Cons 出现时，由 Cons 写分；两块都出现时，Pros 不写分，Cons 写分。N/A 维度不得出现在 Pros/Cons。
- **Pros 门槛**：总体印象分大于等于 3.0 时才常规写 Pros；总体印象分低于 3.0 时默认写“无”，只有材料能证明某个局部明显超过题目预期，或人工记录明确认可为突出亮点时才例外。完成基础要求、页面能运行、存在代码或“主体不是空壳”等不算突出亮点。满足门槛只是允许写，材料没有真亮点仍写“无”。Cons 不为凑数硬写。
- **内容 = 事实清单**：只写"首轮产物只有开始界面点击都进不去游戏""没有麦片收藏""调试4次收敛"这类可观察现象，带轮数/次数/数值/文件名；多个缺陷用"也没有…没有…等"或分号串成整句，禁止"标题：名词清单"式词条结构和斜杠列表（"标题/时间/LIVE"→"标题、时间、LIVE 都没改"）；禁"值得注意的是/整体而言/展现了良好的/有效地"等 AI 腔；
- **轮次语言**：事实涉及迭代过程时，用“首轮/之后/最后一轮/又/才/还是/结果”等词说明变化；静态事实不强塞过程词。用“首轮产物…”“又经两轮调试…”“达到轮数上限”“debug N 次收敛”描述收敛过程，不写“模型展现了高效的调试能力”；
- **口语与评价**：可以自然使用“基本/根本/全没/比较/很/勉强/碰巧/反正”等口语词，但不强制每条添加。评价必须跟具体事实，不能用“能打”“很稳”“完成度高”等词替代证据；禁四字标签（一次成型/盲改直出/零验证零收敛/空满足/巧合命中 → 改“一遍就过了/直接编/没验证也没收敛/碰巧改对”）；
- **对外可读性（去编号化）**：Pros/Cons/Style 面向未看过 rubrics 的读者，**全文不出现 R1-xx/R2-xx 编号与"rubric"字样**——改用"第一轮/第二轮"轮次词 + 现象 + 文件名/数值的人话（如"第二轮把蓝线改成了 #2563EB，标注要的是 #0891B2 那种青蓝"）；悬空术语必须展开（"25 项标注"→"第二轮反馈图里标出的 25 处修改点"、"空满足"→"算它空改对了，反正第一轮本来就没箭头"）；rubric 编号只保留在机器证据节与内部核对表；后端题用 `文件:行`（`models/Product.js:5:23`）这类读者直接可读的证据；
- **密度上限**：单条括号数据不超过 2 个（色值/坐标/行号任选），数值只挑关键的，不把同一条塞成压缩摘要；
- **删五类**：① 元标注——"——G1/G2/G3 加分依据""打分人裁定认可的积极点""总体印象 0.5 的核心依据"等全删；② 日期前缀——"0814 问题 2"式前缀全删；③ 解释从句——"出题人实测'根本玩不了、游戏玩法与核心呈现几乎不达标'"→ 只留"根本玩不了"；④ 重复措辞——"人评口径：开关本身判 1、缺陷由 R1-07 扣"→ 直接"R1-07=0"；⑤ 四字标签（见上）；
- **合并与拆分**：① 同一块内同一维度的多条事实合成一条；② 同一因果链且属于同一维度的事实可用分号连接；③ 跨维度内容拆成多个单标签条目，不用斜杠、加号或“与”拼接标签。
- **句式模板（动态）**：承担分数的条目写成 `【维度名】：给了X分，` + 具体事实；同一标签同时出现在 Pros 和 Cons 时，Pros 写成 `【维度名】：` + 具体亮点，Cons 承担唯一一次分数说明。每条写清可观察的对象、动作或状态、结果；Fingerprints = 行为习惯一句话（如"思考过程习惯中英文夹杂""默认交付深色界面""没有计划过程，直接上手开始写"）。
- **具体措辞**：汇总、排序理由、Pros/Cons 都保持简洁，并写清“对象 + 行为/状态 + 结果”。禁止只写“核心能力比较能打”“主体功能站得住”“整体不错”“大体能跑”“基本成立”“不是空壳”等抽象判断；例如把“核心推箱能力比较能打”改成“探针跑过三关通关，作弊退 17 步再前进 17 步能回到原位”。
- **允许不规整**：两种语序同篇混用、半角分号与"；然后"式连句、空格不一致（给了2.5分 / 给了 2.5 分）都不必统一；不做列表编号、不用加粗；无编号可对的报告类缺陷以"——记报告"或"——S1 扣分点"收束。

**落盘前自查清单（写完 Pros/Cons/Style 必须逐条核对，任何一条不满足就改到过为止）：**

- [ ] 全文无 R1-xx/R2-xx 编号、"rubric"字样（编号只保留在机器证据节与内部核对表）；
- [ ] Pros 块内、Cons 块内分别检查标签；各块没有重复维度标签，重复事实已合并；
- [ ] 所有标签都严格匹配一个适用且已评分的合法维度名，没有 `/`、`／`、`+`、“与”等混合写法，也没有 `【其他】`；
- [ ] Pros/Cons 合集中，每个出现的维度标签恰好有一次 `给了X分`；两块都有同名标签时分数只在 Cons；X 与该维度建议分一致；
- [ ] N/A 维度没有进入 Pros/Cons；
- [ ] 总体印象分低于 3.0 时 Pros 默认为“无”；若例外保留，材料中有超过题目预期或人工明确认可的突出亮点；
- [ ] 无悬空术语——没看过 rubrics 的读者也能懂（如 "Möbius 指数""msg[95]" 这类必须展开或删掉）；
- [ ] Pros 每条以合法的 `【维度名】：` 开头 + 整句陈述，不是名词关键词堆叠；没有符合门槛的亮点写“无”；
- [ ] 无四字标签、无 AI 腔套话、无"标题：名词清单"式词条结构、无斜杠列表；
- [ ] 汇总文字均包含具体对象、动作或状态、结果，没有“能打”“很稳”“完成度高”等抽象评价代替事实；
- [ ] 每条事实都能在材料中找到出处（交付时附出处清单）。

**标签与分数机械检查（每个模型必做）：**

1. 分别截取 Pros 和 Cons，用 `【([^】]+)】` 提取标签，只接受六个合法维度名；
2. 分别统计两块内的标签次数，任一标签在同一块大于 1 次即失败；
3. 对 Pros 与 Cons 的标签并集逐项统计 `给了\\s*(0|0\\.5|1|1\\.5|2|2\\.5|3|3\\.5|4)\\s*分`：标签只在一块时，该块必须恰好 1 次；两块都有时，Pros 必须 0 次、Cons 必须 1 次；
4. 将提取出的 X 与该模型对应维度的建议分比对，不一致即失败；N/A 维度出现即失败；
5. 总体印象分低于 3.0 且 Pros 不是“无”时标记人工复核，确认是否有超过题目预期或人工明确认可的突出亮点。

**执行流程（每次生成或更新 Pros/Cons/Style 必做，用户无需在提示词里重复交代）：**

1. **通读本规范**：先读「文字反馈速记风格」节全文与「落盘前自查清单」，再动手；
2. **读材料核验事实**：rubrics-{模型}.json（编号→现象映射源）、反馈报告.md、预打分.md、人工打分文档.md、记录.txt、模型对话记录.json——每条要写的事实先找到出处，不得新增材料里没有的事实；
3. **按规则重写**：先按总体印象分和亮点证据决定 Pros 是否写“无”，再按维度归类；每块内同维度合并，跨维度拆成单标签条目；最后按“仅 Pros / 仅 Cons / 两块都有”规则放置每个维度唯一一次数字分数；全文不出现 R1-xx/R2-xx 编号与"rubric"字样；悬空术语展开；
4. **落盘前自查**：逐条过「落盘前自查清单」，并机械统计每块标签和跨块分数次数，全部通过后再交付；同时附每条事实的出处清单；
5. **改动范围**：只改目标模型的文字反馈三块与速记风格说明；分数、机器证据、Vibe 标签、其他模型节、已人工确认内容一律不动（存量改稿模式）。

**rubric 结果 → 维度分映射规则（打维度分、给 Pros/Cons 贴维度前，先读 `references\人评标准V2.1-Pointwise多维度评分.md` 的维度定义与 0-4 分档位表）：**

- G1 指令与约束遵循 ← Explicit/约束类条目得分；漏要求、多轮遗忘前文要求都归这里；
- G2 功能交付完整性 ← 功能/bug 类条目得分 + 4W1H 问题（只评最终轮，看最终产物）；
- G3 任务收敛效率 ← 对话记录修复轨迹 + debug 轮数（不考虑模型调用资源失败，主要看 debug 效率；**debug 上限：多轮 3 次、单轮加功能 5 次、单轮修 bug 3 轮，超限算失败**）；
- S1 视觉审美 ← 图形与媒体类条目得分 + 记录.txt 排版意见（与功能剥离看待）；
- R1 需求理解与澄清 ← 首轮对话提问质量（仅适用模糊需求型题目）；
- A1 架构合理性 ← 模块结构证据（V2.1 暂不考虑，统一标 N/A）。

所有建议分一律标注 `【建议 {x}，待人工确认】`，机器只给建议值。

## 内嵌 V2.1 打分纪律

- 总体印象分与排序严格一致；与 pointwise 均分不必一致——不一致时必须在文字反馈中说明理由；
- 3 分 = 验收线；用扣分/加分思维：不是 3 分必须写扣分加分依据；
- 给 0 分谨慎；不情绪化打分；不因 debug 几轮就全给 0 分；
- Rank 是“只能选一个交付优先选谁”的体感，不是均分排序；
- 指纹 = 相对独特偏好（全员都用不算指纹）；标签有依据就都勾（可多选），没有不硬贴，不搞“每类限一个”；文字反馈不写与标签一样的简洁内容。

## 排序理由与洞察速记风格（短度版 2026-08-21 用户定稿；依据人工手写样例）

适用表单「模型排序」下的「排序理由」「洞察」「难点和思路」三节。与「文字反馈速记风格」同源（短句、事实、结论式），但不是逐模型打分流水账——排序理由回答"为什么这个排前"，洞察回答"这批复现了什么共性"，难点和思路讲"题目卡在哪、出题想考什么"。成稿模式任选：白话叙事版（逐模型一句往下排）或紧凑对比版（一句一模型只写差异），硬上限不变。

**排序理由：**
- 总长硬上限：全节 ≤ 12 行或 ≤ 500 字（含标点、模型名、区分度句）；区分度句独占 2 行（≤ 160 字）；每模型恰好 1 句、≤ 55 字；
- 句内硬上限：模型句分句（逗号隔开）≤ 2 个、分号 ≤ 1 个，禁止破折号"——"；区分度句豁免分句上限（≤ 6 个分句），分号 ≤ 1 个、无破折号；
- 先定性后事实：口语定性开头（"做的最好""最稳""直接编""体验最差"），再带 1 个可观察事实兜底；
- 模型句数字硬上限：每模型最多 1 个关键数字（可带一个分数，如"总分 29/45""28 项只过 4 项"），能不要就不要；分钟/token/资源倍率/缺陷偏移量一律禁用（168 分钟、2460 万、72 倍、7.5 分钟、34 万、3 小时 47 分、262 万、15px 均不出现）；
- 删除：过程细节（截断、重启、续写、上下文耗尽、轮次流水账）、括号清单、转折铺陈（"虽然…但是…"最多一组，不叠加）、逐项报失分；
- 顺序即排序：区分度句后第一句点名第一名（"X 做的最好"），"其次是…/…第三"往下，垫底用"体验最差"收尾，并列合并成一句。
- 区分度句：排序理由开头 1 句总览，回答"这道题凭什么拉开模型、分数差在哪"，指向评分与排名依据；句式照三段式标杆："物理仿真题的真实区分度在「物理是不是真算的、以及算出来的量能不能被验证」：档位最高的一家能量出飞沫从 32 涨到 3 万多个粒子并自己单调回落、把重力从 30 调到 2 后沉降时间拉长约 3.75 倍，这类数字才能证明参数真的接进了求解器；而末位那家把飞溅做成一堆白点、超过某个高度就不显示，条目上「有飞溅」照样成立"：
  ① 点题："这道题的真实区分度在「X」"，X 是题目的可区分维度，讲题本身，不写"这批最拉分的是"；
  ② 最高档证明：1 个证明"真做"的行为 + ≤ 3 组证明性数字，收一句"这类数字才证明它真在…"；
  ③ 末位假象：低分模型的表面达标，句式照"条目上「有飞溅」照样成立"，不点名中间模型、不逐项报失分；
  - 与洞察分工：区分度句讲"分数在哪拉开、证据长什么样"；洞察讲"这批复现的共性、根因、怎么验证"；同一轴线上各取一面，区分度句用数字、洞察讲行为与根因，禁止重复同一数字细节；
  - 字数与数字：≤ 160 字（含标点、模型名；样例 140 字 + 约 15% 余量）、最多 3 组数字；数字分级：证明性数字（证明真算/真做/假做：粒子数变化、重合度 0.52→0.84、28 项只对 4 项、验证产出值如像素差 0.67）可留；过程细节数字（时间/token/资源倍率/缺陷偏移量 15px）依然禁；倍率与像素值不一律禁：资源倍率（72 倍 token）禁、行为效应倍率（3.75 倍沉降）算证明，缺陷偏移量（15px）禁、验证产出值（0.67）算证明；分差扁平（分数挤在一起）时省略，不硬凑。

**洞察：**
- 1-2 句，每句 ≤ 120 字；一句一条共性，句式照素材："这类问题静止时看不出来，必须真的甩一下再看谁跟着走"：结构 = 共性现象（点名 ≤ 2 个模型；"D 除外"式例外锚点不计入限额）→ 根因（有对话原文/报告依据才写，无据降级为"共性 + 验证提示"，不编根因）→ 验证提示（"这类必须看图才修得对的点，静止读代码看不出来，得渲染出来跟目标图比才算数"）；
- 与区分度句分工：区分度句讲分数结构（数字证据），洞察讲能力短板（共性 + 根因 + 怎么验证）；禁止重复同一数字细节，区分度句已写 0.52→0.84 时洞察只讲行为与根因；不逐模型复述分数；数字只允许题面点名词（"25 处标注"），不带证明性数字与分数。

**难点和思路：**
- 题目难点 ≤ 4 条，每条 1-2 句、≤ 60 字；格式 = "现象 + 一个本批案例"；
- 每条最多带 1 个模型例子（"C 就栽在 Central"），禁止括号内列举多个模型（"（D、GLM5.2、B、A、E、Hy3-dev）"这类清单禁用）；
- 考察点/出题思路 1-2 句、每句 ≤ 60 字，白话说明意图与权重，不出现 rubric 编号与"rubric"字样。

**禁止项（三节通用）：**
- 无 R1-xx/R2-xx 编号（改用"第一轮/第二轮"）、无"rubric"字样、无 AI 腔空转词（值得注意的是/整体而言/综上所述/展现了/有效地/不仅…而且…）；
- 无四字标签：一次成型/盲改直出/零验证零收敛/空满足/巧合命中/零交付——改成人话（"一遍就过了""直接编""连交付文件都没交"）；
- 无破折号"——"（改用逗号/冒号/分号）；无术语堆砌（OCR→"文字识别"）；不做列表编号排比收尾；
- 无"第一轮…第二轮…"整段流水账（一节最多提一轮）；
- 不写材料里没有的事实；"它想…"类归因只在有对话原文时写。

**素材例句（3 条）：**
- "opus5做的最好，画面十分写实，完全复刻出了要求中黄金时刻的氛围，沉浸感强。其次是hy3-dev，效率最高，虽然审美一般，但最终产物没有穿模问题……glm的体验还是更差。"
- "k3是最差的，效率最低，审美差，流光动画与传送带传送方向不对应，体验最差。"
- "多数模型会忽略要求中的禁止小球发生穿模。"

**与「文字反馈速记风格」的一致点/差异点：**
- 一致：短句、事实、结论式；口语词（基本/根本/只敢/碰巧/反正）；无编号、无四字标签、无 AI 腔；每条事实有出处。
- 差异：Pros/Cons 是“单一维度标签 + 具体事实”的评分笔记，每个维度在 Pros/Cons 合集中只写一次分数；排序理由/洞察/难点和思路是压缩版，只留定性 + 一个关键事实，数字一律砍掉；区分度句例外，允许 ≤ 3 组证明性数字。
