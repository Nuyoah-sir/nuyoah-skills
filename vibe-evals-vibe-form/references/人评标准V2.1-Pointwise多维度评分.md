# Coding Agent 人评表格作业标准 V2.1（1022 更新版）—— 3. Rubrics 与维度打分（权威转录）

来源：`../references/Coding Agent 人评表格作业标准 V2.1.md` 的 §3.1—3.5（腾讯文档 1022 更新版，逐屏截图转录，〔?〕 为原文存疑处）。本文件是「打维度分、写 Pros/Cons」的权威依据；**Rank 与洞察见全文 §4，Vibe Tags 见 §3.4 与标签库**，本文件不覆盖。

> 与 0917 版的差异（读完下面各节再看这四条）：① 维度从 6 个减到 **5 个**，R1「需求理解与澄清」不再单列；② 任务收敛效率不再写 0—4 档描述，改为**按 Debug 轮次查表**；③ 维度分不再按 0—4 档描述判定，改为 **通过权重 ÷ 总权重 × 4，向下取 0.5**，Baseline 另按条扣分；④ Pros/Cons 句式统一为 `【维度】：Rubrics：通过数 / 总数，维度总结与感受`。

## 3.1 Rubric 字段与 Baseline 检查

每条 Rubric 描述一个 Yes / No 判定项，评测员逐条判定后计算维度分。**判定与文字描述均由人工完成，不得交给 AI 代判、代写。**

| 字段 | 取值 | 填写要求 |
| --- | --- | --- |
| item_id | 如 R0-01、R1-02 | R0-01 = 第 1 轮第 1 条；R1-02 = 第 2 轮第 2 条 |
| criterion | 自由文本 | 必须是能用 Yes / No 回答的判定项 |
| type | Objective / Subjective | Subjective 多见于审美类 |
| necessity | Explicit / Implicit | Explicit：Prompt 或历史上文明写的；Implicit：需推理得出 |
| priority | Must have / Nice to have / Beyond expectations | 分别对应任务必要、优先实现、超额预期；Baseline 一般划 Must have |
| dimension | 指令遵循 / 功能完整性 / 视觉审美 | 可单选或多选（数组） |
| weight | 0.5 / 1，默认 1 | Baseline 不设此字段 |
| score | 0 / 1 | 通过记 1，不通过记 0，**不给部分分** |

Rubric 总条数以 30 条以内为宜，每个适用维度至少 5 条判定点。

**Baseline 成败检查**

- Baseline 是几乎所有模型都应通过、但仍须检查的底线要求，**独立列出，不计入维度权重与原始分**。
- 检查 4 次：首轮 Prompt 执行交付物、Debug 前产物、各轮 Debug 后产物（3 轮 Debug）。
- 任意一次判定不通过即计 1 条出错；**后续轮次已修复仍计出错**，只在 Cons 记修复状态。
- 扣分口径：错 1 条在对应维度扣 1 分，同维度错 N 条扣 N 分，扣到 0 为止；一条标多个维度的，各维度各扣 1 分。
- 维度归属：默认「运行可用」→ 功能完整性，「基础可读与可操作」→ 视觉审美。
- 判定用否定式表述：「是否未出现 xx 情况」，Yes = 通过。

两类检查示例：运行可用（按交付说明运行后是否未出现白屏、崩溃、持续加载导致不可用）、基础可读与可操作（正常视口下是否未出现重要文字或控件因重叠、遮挡、溢出、错位而不可读不可操作）。

**Priority 三类**：Must have = 完成本题必须具备的功能、内容与效果；Nice to have = 同类功能的优秀实现，更自然流畅美观易用，多在视觉与交互；Beyond expectations = 其他模型从未实现、且人确实感到意外，预期表现不写、不预留权重。

## 3.2 五个维度

| 维度 | 评分方式 | 评什么 |
| --- | --- | --- |
| 指令与约束遵循 | 依赖 Rubric（dimension=指令遵循） | 是否理解需求、漏没漏需求、多轮是否遗忘前文、是否违反 Prompt 明写的约束 |
| 功能交付完整性 | 依赖 Rubric（dimension=功能完整性） | 已实现的功能和核心链路有没有 Bug、影响多大；以最终产物为准 |
| 视觉审美 | 依赖 Rubric（dimension=视觉审美） | 带前端页面的题目看排版、颜色、动效等观感，须与功能分开判断；**主观分必须人眼判定** |
| 任务收敛效率 | 按 Debug 轮次查表 | 经过几轮 Debug 才修好反馈的问题 |
| 架构合理性 | 不依赖 Rubric | 前端题目一般不打 |

**任务收敛效率查表**：0 轮 = 4 分；1 轮 = 3 分；2 轮 = 2 分；3 轮且反馈问题全修好 = 1 分；3 轮仍有未修好的问题或核心功能仍不可用 = 0 分。每多 1 轮扣 1 分，不因其他因素调整；核心功能仍不可用直接 0 分。

**不适用维度填「-」**，并在 Pros/Cons 说明原因；适用的维度不得填「-」或留空。

## 3.3 单维计分与分档

- 总权重 = 该维度全部计分条目的 weight 之和（Baseline 不计入）
- 通过权重 = 判定通过条目的 weight 之和
- 原始分 = 通过权重 ÷ 总权重 × 4
- 分档：**向下取到最近的 0.5**，不四舍五入（3.2→3.0、3.7→3.5、3.04→3.0；恰好落在分档上不变）
- 视觉审美类允许在群里说明后做特殊调整
- 维度最终得分 = 分档后的得分 − 该维度 Baseline 出错条数，下限 0

例：功能交付完整性原始分 3.57 → 分档 3.5；「运行可用」在 Debug 前产物白屏（No）扣 1 分 → 2.5；若另有 1 条 Baseline 出错 → 1.5。

## 3.4 Pros / Cons 汇总

**填写格式**：`【维度】：Rubrics：通过数 / 总数，维度总结与感受`；权重不同时可同时注明通过权重 / 总权重。不要把条数通过率当计分依据。不依赖 Rubric 的维度也要按 `〔?〕` 汇总。

**归类要求**

- 任务收敛效率只能在 Pros 或 Cons 选一边；只写 Debug 轮次与修复情况（共几轮、每轮反馈什么、哪些修好哪些没修），不写对话、页面使用、耗时、资源占用。
- 允许低分维度同时记优缺点：某维度只有 1 分，但做到了别人没做的点，可在 Pros 与 Cons 分别记。
- Baseline 未通过**不算功能缺陷**：在 Cons 加 `【成败问题】` 条目，写明出现在哪一轮、是否修复；已修复不改变 3.3 的扣分，只记修复状态。

## 3.5 总体印象评分

以维度均分为基准，**允许 ±0.5 浮动**，超出即违规。示例：均分 2.5 时可取 2 / 2.5 / 3；均分 3 时可取 2.5 / 3 / 3.5。先明确这道题主要考什么，再结合核心验收点决定落在区间哪一端。
