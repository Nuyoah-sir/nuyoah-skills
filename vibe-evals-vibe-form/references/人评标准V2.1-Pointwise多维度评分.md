# Coding Agent 人评标准 V 2.1 —— 四、Pointwise 多维度评分（权威原文转录）

来源：`Coding Agent 人评标准 V 2.1.docx`。本文件是维度打分与 Pros/Cons 贴维度的权威依据，打维度分、写文字反馈前必读。

## 标注四件套

每个模型回复 = 1 个总体印象分 + pointwise 多维度打分 + Vibe Tags + 1 个备注（pros/cons/stylistic fingerprints 三块）。

- 总体印象分：0–4，允许 0.5 档；
- Pointwise：每维度 0–4，允许 0.5 档；
- Vibe Tags：只选最突出的点，没有不硬写；
- 备注三块：pros/cons/stylistic fingerprints，补充标签覆盖不到的点；维度打分依据也写在 pros/cons 里，且不写和标签一样的简洁内容。

## 打分总原则

- 用扣分和加分思维打分，标准是 3 分：达到验收标准 = 3 分，超过预期加分，低于预期扣分；
- 不是 3 分的，都要给出扣分/加分依据，在 cons 和 pros 里说清楚；
- 不情绪化打分；debug 几轮不全部给 0 分；给 0 分要谨慎；
- 总体印象分与 rank 严格一致，与 pointwise 各维度均分不必严格一致，趋势不符要复查。

## debug 上限

多轮 debug 上限 3 次；单轮加功能 5 次；单轮修 bug 题目 3 轮。多轮题 3 轮 debug 后仍达不到 3 分（可用标准），算该轮失败。

## 六个维度（定义 + 0–4 分档位）

### G1 指令与约束遵循（通用，不可 N/A）

定义：是否准确落实显性指令、硬性限制和复杂组合约束，不擅自改变任务目标。评估是否有"照做需求"，漏了要求在这扣分；多轮题目对前文要求的遗忘也归这个维度。

- 0：完全无视核心指令或硬性约束，自作主张（如选错语言/框架），结果南辕北辙。
- 1：仅遵循极少部分宏观指令，丢失大量关键约束（命名规范、API、格式完全失控），需大规模重构。
- 2：核心约束基本执行到位，但次要规则明显违背（忽略文件结构、混用库），需人工排查修正。
- 3：严格遵守所有显性指令和硬性约束，代码格式规范，不越界、不漏项，表现符合预期。
- 4：100% 遵守所有约束，在极端复杂复合指令下展现极强控制力；主动避开未写明但潜在的冲突点。

### G2 功能交付完整性（通用，不可 N/A）

定义：关键功能、核心链路是否正常实现，没有 bug；bug 程度有多大。目前只评最终轮，看最终产物。

- 0：严重语法错误无法编译/运行；前端白屏报错；核心功能一项都未实现。
- 1：勉强能跑，但主干链路断裂/存在阻断性 Bug；仅实现极少部分核心需求，无法投入使用。
- 2：主业务跑通，核心功能可用，但存在非关键 Bug 或缺边界处理（遇空数据崩溃），须人工修补。
- 3：核心流程完全闭环，运行流畅无明显 Bug，边界处理得当，交付可直接运行的完整成品。
- 4：功能完美运行无 Bug，在鲁棒性、性能优化或扩展性上有突出表现（防抖节流、容错机制），体验超预期。

### G3 任务收敛效率（通用，不可 N/A）

定义：任务目标和当前阶段要求明确后，能否通过实现、验证和修正使任务高效稳定达到可验收状态。重点看首轮实现基础、每轮有效进展、根因定位、重复犯错、修改范围、回归和最终收敛；轮次仅参考。不考虑模型调用资源失败导致的原因，主要关注 debug 效率。

- 0：上限 5 轮的：5 轮无法修复；上限 3 轮的（单轮修 bug 题 + 多轮题）：3 轮仍无法交付（多轮题算每轮平均 debug 轮次）。
- 1：上限 5 轮的：3-4 轮无法修复；上限 3 轮的：2 轮仍无法交付。
- 2：上限 5 轮的：2-3 轮无法修复；上限 3 轮的：1 轮仍无法交付。
- 3：上限 5 轮的：首轮已形成正确主体，后续少量针对性修正，只需 1 轮 debug；上限 3 轮的：1 轮能交付。
- 4：不需要 debug，首轮即高质量实现；或遇问题主动验证、快速定位根因、最小必要改动修复，几乎无无效尝试、重复错误和功能回归，低人工协作成本达高质量验收。

### S1 视觉审美（前端维度，不适用可 N/A）

定义：前端界面的布局、层级、配色、风格一致性，以及与参考图或主题的匹配程度。带前端页面（含全栈/多端）的美观度：物体建模、颜色、动效等；需与功能剥离看待，功能好画面可能粗糙，反之亦然。

- 0：页面错乱或样式基本失效，无法正常阅读和使用。
- 1：有基础框架，但布局、层级、配色或比例存在严重问题。
- 2：核心元素存在，整体可用，但视觉粗糙、模板化或与目标有明显偏差。
- 3：排版规整、层级清晰、风格协调，达到正常产品或现代 UI 的预期。
- 4：在满足功能和题目风格要求基础上，视觉设计、细节和交互明显优于普通交付，且不过度装饰。

### A1 架构合理性（后端维度，不适用可 N/A；目前无后端题暂不考虑）

定义：模块职责、代码边界、接口与数据契约是否清晰，修改和扩展成本是否可控。

- 0：逻辑混杂、职责不分，结构无法维护，需推翻重写。
- 1：形式上有文件或分层，但边界严重混乱、重复代码多，修改影响面失控。
- 2：基本结构存在，但部分职责越界、契约不一致或扩展成本较高。
- 3：分层和模块边界清楚，职责、接口和数据契约合理，修改范围可控。
- 4：不过度设计前提下，为真实可预见的扩展、错误处理、事务或兼容性提供清晰机制。

### R1 需求理解与澄清（模糊需求维度，不适用可 N/A）

定义：实施前能否准确理解用户真实意图，识别影响方案和验收结果的关键歧义，并通过必要提问、明确假设或提供选项使需求达到可执行状态。仅适用模糊需求型、需要模型先定方向的题，主要关注首轮提问质量。

- 0：完全无识别能力。对模糊需求装作清楚，硬猜实现；产物与真实意图严重偏离；不提任何澄清问题。
- 1：有"可能没理解"的意识但不行动。只写一两句"如果不对请告诉我"敷衍备注，仍按错误假设硬干；澄清问题缺失或只问无关格式细节。
- 2：能问问题但不到位。识别 1-2 个明显模糊点并提问，但漏掉关键决策点（业务边界、数据口径、性能要求）；问题颗粒度过粗或过细。
- 3：澄清问题准确且必要。第 1 轮主动提 2-4 个真正影响实现的关键问题（业务边界、技术选型、数据范围等）；对自行假设明确标注"我假设了 X，如不对请告知"。
- 4：澄清 + 决策建议。除提问外给出各选项权衡与推荐方案；识别隐性需求并主动验证，让用户最少轮次内完成需求收敛。

## 排序理由与洞察（官方口径）

- Rank：同一题下多模型相对比较，回答"只能选一个交付优先选谁"，不是均分排序；先独立整体判断，再用分数一致性检查。总体印象分与 rank 严格一致。
- 排序理由：写"分水岭" 1-3 句，覆盖相邻档位关键差异，只写可观察事实，不写名气/偏好；有并列说明为何证据不足以拉开。
- 洞察：两个维度——最大模型差异（哪个环节真正拉开差距）+ 能力边界 Insight（AI 已能做什么、哪些还需人纠正）。写共性问题，不写"A 视觉最好、C 漏了行人"这类单模型复述。
