# Coding Agent 人评表格作业标准 V 2.1

## 0. 评测目的与流程

- **评测对象**：评测 Coding Agent 完成编程任务的能力，包括交互调试体验与交付物质量，记录不同模型带来的真实体验差异。
- **核心目的**：测试同一任务交给不同模型时，经过模拟真实用户操作的 Debug 反馈后，谁做得更到位、产物更好用、交付更贴合 Prompt 预期。
- **评测原则**：以最终产物为依据，不因链路问题导致的体验差异主观加减分；Debug 判断与反馈、各维度打分、排序与洞察均须人工完成，不得交由 AI 代判、代写。

**评测总流程**：

| 阶段 | 要求 |
| --- | --- |
| 评测准备 | 使用最新版 CodeBuddy，确认模型权限、关闭记忆、开启 max 模式；每〔此格在原文档中被表格右缘截断，后续文字不可见〕 |
| 执行与调试 | 按规定 Prompt 执行，对获得产物按规定 Debug，最多 3 轮 |
| 保存记录 | Debug 结束后立即上传 Trace ID、history 与最终产物 |
| 评测与排序 | 按 Rubric 计算维度分，打总体印象分，填写 Pros / Cons；全部模型完成新〔此格在原文档中被表格右缘截断，后续文字不可见〕 |
| 提交与自检 | 录制并上传讲解视频，补齐作业表，按自检清单核对 |

## 2. 执行与调试

### 2.1 Prompt 交互

在 Codebuddy 内图形交互界面，使用正确的工作空间（如有题目附件请按要求放入），并输入当期负责题目的正确 Prompt 版本、模型，与 Agent 进行单轮/多轮常规交互。

### 2.2 Debug 调试 ✍️✍️✍️✍️

**Debug 基本原则**：

人评作业需要记录真实使用 Agent 时的 Debug 行为：是否 Debug、进行几轮、每轮 Prompt 怎么写，都由评测员人工判断和填写，不得让 AI 代填代写。反馈时以不了解该题细节的用户身份，用自然语言描述实际使用中发现的问题。

Debug 范围是 Rubrics 中的「明显缺陷」条目：

- 需要 Debug：有 must have 类 Rubric 未通过，或产物出现 Rubric 之外的明显不合理问题、严重影响的 bug。
- 不进行 Debug：只有 nice to have 类 Rubric 未通过。

**轮次与内容要求**：

同一题目下每个模型最多 Debug 3 轮：多轮项目按队列依次提交每一轮 Prompt，全部运行完成后再统一 Debug。每轮反馈前，先对照 Rubric 的考察点全面检查产物，再把发现的问题一次性、尽可能完整地反馈给模型。

反馈内容要求如下：

- 必写：错误调整需求。
- 可补全：第 2 轮 Debug 后仍未达到要求时，可以说明明细达到的现象。〔?〕

**注意事项**：

反馈只描述问题现象，确保模型在「真实用户」一样的反馈下自行修复，具体要求如下：

- 【红字】不得预设模型〔warrant?〕在 Rubric 假内容，如〔探索靶?〕未通过的 Rubric 条目。（此句两轮精读仍无法完全辨认，需对照原文）
- 不得把其他模型负责判断的内容直接发给被测模型。
- 不得使用 AI 撰写 Debug 轮内容。
- 不得在两轮 Debug 中间再告诉模型如何修改。
- 不得在同一对话中让当前被测模型检查自己的产物。

## 3. Rubrics 与维度打分

### 3.1 Rubrics 说明

每条 Rubric 描述一个 Yes / No 判定项，评测员根据模型产物逐条判定，再计算各维度的得分。

【红字】Baseline 检查标准：Debug 前以及各轮 Debug 后的产物（限 3 轮 Debug，共需检查 4 次）均按 Rubric 计算产物分数。

二期照用一期的软化：Baseline（基线）独立列出，不计入维度权重与原始分计算，但按 3.3 节规则对对应维度按条扣分；Priority 扩展为三类，新增 weight 权重字段。〔句首数字〔?〕〕

**字段说明**：

| 字段 | 取值 | 填写要求 |
| --- | --- | --- |
| item_id（编号） | 如 R0-01、R1-02 | R0-01 表示第 1 轮第 1 条；R1-02 表示第 2 轮第 2 条 |
| criterion（判定点） | 自由文本 | 必须是可用 Yes / No 回答的判定项（见下方示例）〔?〕 |
| type（类型） | Objective / Subjective | Objective：可客观判定；Subjective：主观判断，常见于审美类条目〔此格沿用初稿转写〕 |
| necessity（必要性） | Explicit / Implicit | Explicit：Prompt、历史上文明确写出的要求；Implicit：需要推理得出、符合具体实现的要求 |
| priority（优先级） | Must have / Nice to have / Beyond expectations | 三类分别对应任务必要、优先实现、超额预期；Baseline 问题一般都划为「Must have」 |
| dimension（评测维度） | 指令遵循 / 功能完整性 / 视觉审美 | 可单选或多选（数组），维度含义见 3.2 |
| weight（权重） | 0.5 / 1，默认 1 | 如需调整需与质检、产品达成共识〔?〕；Baseline 不设置此字段 |
| score（分数） | 0 / 1 | 按 rubric 打分填写 score 字段：对 criterion 通过（Yes）记 1，不通过（No）记 0 |

Rubric 总条数以 30 条以内为宜，题目复杂时可超过 30 条；每个适用维度至少对应 5 条判定点。

**Baseline 成败检查**：

- Baseline 是基本所有模型都应通过、但仍须检查的底线要求。
- 检查范围：首轮 Prompt 执行交付物、Debug 前产物，以及各轮 Debug 后的产物（3 轮 Debug 共检查 4 次）。
- 只要有任意一次检查中该条目判定为不通过（No），即计为 1 条出错；后续轮次已修复的，仍计为出错，仅写入修复状态。
- Cons【成败问题】：判定结果填写在作业表「Baseline成败Rubrics」列；如果出现错误，汇总中需要作为 Cons:【成败问题】记录，格式见 3.4 节。〔条件句部分难辨〕
- 扣分口径：Baseline 不参与权重与原始分计算，但按条对应维度扣分——错 1 条，在该条目标注所在维度的得分上扣 1 分；同维度错 N 条扣 N 分，扣至 0 分为止（计算方法见 3.3 节）。
- 维度归属：Baseline 条目须标定 dimension（见 3.3 节），默认「运行可用」对应功能完整性，「基础可读与可操作」对应视觉审美；一条条目标注多个维度的，各维度分别扣 1 分。主要包括以下两类。

**检查示例**：

| 检查类型 | 判定示例 |
| --- | --- |
| 运行可用 | 按交付说明在要求的本地环境中运行后，是否未出现白屏、崩溃或持续加载异常导致核心程序或 Web 后台无法使用的情况？ |
| 基础可读与可操作 | 在目标设定的正常视口下，是否未出现重要文字或必要操作控件因重叠、遮挡、异常溢出、布局错位而无法阅读或操作的情况？ |

对此类问题，统一使用「是否未出现 xx 情况」的否定式表述：确答 Yes = 通过，记 1；No = 不通过，记 0。〔句首两字〔?〕〕

**Priority 三类**：

| 关键词 | 判定标准 |
| --- | --- |
| Must have | 除延续外〔?〕，完成本题必须具备的功能、内容和效果，缺少这些，产物就没有完成用户交代的任务 |
| Nice to have | 同类功能的优秀实现。在基本要求之上做到更自然、流畅、美观、易用〔?〕，多为视觉审美与交互体验 |
| Beyond expectations | 其他同类模型从未实现、新模型做到了，且人确实感到意外、震撼。预期表现就不写，也不预留权重；不确定时在群里讨论 |

区分示例：同一题中，golden answer 用二维地图展示玩家标注位置，并随移动同步更新，帮助判断所标注区域，这属于可以预期的优秀实现，归入 Nice to have；人没有想到、模型却做到了，并带来明显惊喜的，才归入 Beyond expectations。

**Rubric 编写与修订**：

- 以下规定 Rubric 的格式、拆分合并和评审中迭代要求：拆分与合并仅在修复环节处理，判分规则见 3.3。
- Rubric 以 JSON 数组记录。单维度用字段，多维度用数组；Baseline 沿用原有子段格式及 0/1 判定方式，但不设置 weight，以精简子段结构〔?〕，具体判定点以当期题目为准。

**单维表示例**（代码块）：

```json
[
  {
    "item_id": "R0-01",
    "criterion": "是否按 Prompt 要求交付 svg 代码文件？",
    "type": "Objective",
    "necessity": "Explicit",
    "priority": "Must have",
    "dimension": "指令遵循",
    "weight": 1
  }
]
```

**多维版示例**（代码块）：

```json
[
  {
    "item_id": "R0-32",
    "criterion": "玩家位置变化时，二维地图中的位置标记是否同步更新并清晰可辨",
    "type": "Objective",
    "necessity": "Implicit",
    "priority": "Nice to have",
    "dimension": ["视觉审美", "功能完整性"],
    "weight": 0.5
  }
]
```

### 3.2 维度介绍

评测任务共关注 5 个维度，其中「指令与约束遵循」「功能交付完整性」「视觉审美」依据 Rubric 判分，计算方法见 3.3 节；「任务收敛效率」和「架构合理性」不依赖 Rubric。

**各维度评分概览**：

| 维度 | 评分方式 | 评什么 |
| --- | --- | --- |
| 指令与约束遵循 | 依赖 Rubric：dimension 对应「指令遵循」 | 是否理解需求、遗漏需求、多轮累计遗漏前文要求，以及违反 Prompt 中明确给出的约束，归入此维度 |
| 功能交付完整性 | 依赖 Rubric：dimension 对应「功能完整性」 | 已实现的功能和核心链路是否有 Bug、影响程度多大；以最终产物为准〔?〕 |
| 视觉审美 | 依赖 Rubric：dimension 对应「视觉审美」 | 带前端页面的题目（含全栈、多端开发）的视觉观感，包括清晰排版、颜色、动效等，须与功能表现区分判断；主观分必须人眼判定，禁止交给模型判断 |
| 任务收敛效率 | 按 Debug 轮次 | 经过几轮 Debug 才修复反馈的问题，具体分值见下表 |
| 架构合理性 | 不依赖 Rubric | 前端题目一般不打 |

> ⚠️ 不适用维度：填「-」，并在 Pros / Cons 中说明原因；适用的维度不得填「-」或留空。

**任务收敛效率参考**：

| Debug 情况 | 得分 |
| --- | --- |
| 0 轮 | 4 分 |
| 1 轮 | 3 分 |
| 2 轮 | 2 分 |
| 3 轮，反馈问题均已修复 | 1 分 |
| 3 轮，反馈的问题仍有未修复，或核心功能仍无法使用 | 0 分 |

该维度只与 Debug 轮次和修复结果挂钩：第 3 轮且反馈问题均已修复记 1 分；满 3 轮后仍有 Must have 类问题未修复，或核心功能仍无法使用，记 0 分。每增加 1 轮扣 1 分，不因其他因素调整。开始执行 Debug 轮前开展过多少轮对话、模型调用资源次数等情况不计入；核心功能仍无法使用按 0 分处理，例如前端小游戏连打开游戏都无法完成。

### 3.3 Rubrics 打分与维度分数 👍👍👍

**评分参考**：

每条 criterion 只判通过或不通过：通过记 1，不通过记 0，不给部分分。weight 表示该条目在计分中的占比，权重为 0.5 不代表「部分通过」。

【红字】判定与文字描述均由人工完成，不得交给 AI 代判、代写。

**单维计分**：

「指令与约束遵循」「功能交付完整性」「视觉审美」三个维度分别计算。将对应维度全部计分条目的权重与其中通过条目的权重分别相加，再按比例缩放为 4 分制。Must have、Nice to have、Beyond expectations 均参与计算，Baseline Rubrics 均不参与维度计算。

- 总权重 = 该维度全部计分条目的 weight 之和
- 通过权重 = 其中判定通过条目的 weight 之和
- 原始分 = 通过权重 ÷ 总权重 × 4

计算示例：某维度共 18 条计分 Rubric：

| weight | 总条数 | 通过条数 | 总权重 | 通过权重 | 原始分 | 最终得分 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 10 | 6 | 10+4=14 | 6+3=9 | 9 ÷ 14 × 4 ≈ 2.57 | 向下取整 = 2.5 |
| 0.5 | 8 | 6 | | | | |

**分档调整**：

维度得分以 0.5 分为步长，将原始分向下取到最近的 0.5 分档，不四舍五入。其中，「视觉审美类维度」允许特殊情况下调整，但需要在题目协调群说明特殊情况原因。

- 例如：3.2→3.0、3.7→3.5、3.04→3.0；原始分恰好落在分档上时保持不变，如 2.0→2.0。
- 「视觉审美」维度 2.57 分，经评测群内主观性判断调整为 3 分。〔?〕

**Baseline 扣分**：

Baseline Rubrics 不计入总权重与通过权重，而是在分档后的维度得分上单独扣分：

- 扣分数 = 该维度下判定出错的 Baseline 条数 × 1 分
- 维度最终得分 = 分档后的维度得分 - 扣分（下限 0 分）

是否出错以 3.1 节的 4 次检查为准〔?〕：同一 Baseline 在首轮 Prompt 执行交付物、Debug 前产物或任一 Debug 轮产物中判定不通过，即计 1 条；后续轮次已修复不改变扣分，仅在 Cons【成败问题】中写明修复状态。

举例：功能交付完整性原始分 3.57，分档后为 3.5 分；「运行可用」在第 1 轮 Debug 前的产物中出现白屏（No），扣 1 分，该维度最终得分 2.5 分；若该维度另有 1 条 Baseline 出错，再扣 1 分为 1.5 分。

可使用 📄 Rubric-评分工作表-1023.html 辅助计算（有使用问题及时反馈），Rubric 的通过与否则须人工判断。

### 3.4 Pros / Cons 汇总

Pros / Cons 汇总是对各级维度表现的汇总，须写明对于 Rubric 通过情况的分维度总结，不只写「好用」「效果差」等笼统感受。

**填写格式**：

ProsCons:【维度】：Rubrics：通过数 / 总数，维度总结与感受，权重不同时，可同时注明通过权重 / 总权重。避免将条数通过率误作为计分依据；不依赖 Rubric 的维度也要按〔?〕汇总，但不强依赖 Rubric 通过情况。

**填写示例 1**：

- Cons：
  - 【功能交付完整性】：Rubrics：6 / 16（权重均为 1），扩展点是正确的，但最终交付仍不完整；测试因适配容报错〔?〕，新闻模块不全，分裂恒简或未真实实现〔?〕；分裂后运动未合理扫描子网〔?〕，配置字段未跟进对齐。
  - 【任务收敛效率】：测试第 2 轮、真实第 3 轮〔?〕，配置生成问题在第 3 轮 Debug 后仍未修复，未完成问题验证闭环。

**填写示例 2**：

- 【底层问题】：首轮按交付说明运行后页面白屏，无法使用；第 1 轮 Debug 后已修复。〔标签「底层问题」按截图转写，3.1 节统一用语为「成败问题」〕

**归类要求**：

突出优点写入 Pros，突出缺点写入 Cons，有如下注意事项：

- 任务收敛效率只能在 Pros 或 Cons 中选择一项填写，不要重复在两处。
- 任务收敛效率只能写 Debug 轮次与修复情况：共几轮 Debug，每轮反馈了什么、哪些修好了，哪些没修好。不得提及与对话、页面使用、生成耗时、资源占用等与收敛效率无关的内容（此类内容需写入边缘维度或洞察）〔?〕。
- 允许模型在单一维度内得分偏低但仍有突出优缺点的记录〔段意如此，原句部分难辨〕：某功能对应维度仅 1 分，但实现了其他模型都没有实现的一个点，可以分别记录该维度的突出优缺点表现在 Pros 和 Cons。

**Baseline 未通过的处理**：

Baseline 未通过时不视为功能缺陷，而是需在 Cons 中以【成败问题】条目额外标注问题，并写明出现在哪一轮（首轮 / Debug 前 / 第 N 轮 Debug 后）及该条是否修复；不把 Baseline 的错误在其他维度描述为最终产物的缺陷。注意：已修复不改变 3.3 节的扣分，仅作为修复状态记录。

### 3.5 总体印象评分

作业表「维度均分」作为参考。总体印象分以维度均分为基准，允许在 ±0.5 分范围内浮动，评测员最终定稿时保留主观判断〔?〕。

- 示例：维度均分 2.5 分时，总体印象分可取 2 分、2.5 分或 3 分；维度均分 3 分时，可取 2.5 分、3 分或 3.5 分。
- 评测前先明确该题目主要考察什么，再结合题目的核心验收点判断模型在核心内容上的完成情况，在区间内取值。
- 示例：题目主要考察视觉表现，模型的视觉审美明显较好，但任务收敛效率或功能交付存在一些问题，总体评分仍可在允许范围内取上限（如以 2.5 分取 3 分）。
- ⚠️ 总体印象分不得超出维度均分 ±0.5 的范围。

## 4. GSB 排序与洞察

### 4.1 排序原则

- 当期评测要求对同一题涉及的所有模型产物进行总体排序（需要与过往模型评测结果比较时，【红字】必须重新查看对应题目的具体评测记录，做到排序留档〔?〕）。
- 总体印象分可同分不同序：允许两个模型总体印象分相同但排序不同，须在排序理由中说明同分不同序的原因。
- 总体印象分以维度均分为基准，上下浮动不超过 0.5 分（见 3.5 节）。

### 4.2 排序理由

排序理由须写明排序相邻模型的关键差异：有并列时，说明为什么现有证据不足以排出模型间的优劣；非并列时，说明名次与表现/内容/整体出于模型特质的理由。由于模型排序与模型总体印象的分数挂钩，排序理由可视为总体印象的缩影与基于客观事实的主观体验〔?〕。

例题：使用纯 SVG 代码绘制一个等距视角（Isometric）的微缩城市，包含道路、建筑、公园、树木、车辆和行人。要求整体细腻完整，具有立体感和统一风格，不要使用任何 HTML、CSS、JavaScript，只输出完整 SVG 代码文件。

【红字】排序理由示例（部分模糊〔?〕）：「A 创意强，建筑、公园、树木、车辆和人物体补充全，等距方向也一致；B 虽有绘制人物，但右侧建筑的处理层次是反的；C 画面虽丰富，但在 SVG 中出现了出框〔?〕，还反了字体块〔?〕，因此综合排序 A > B > C。」

错误示范：「A 没有好啊，B 大块。C 能跳。」（只是表述感受，没有说差异）

### 4.3 评测洞察

作业表 insights 栏需要至少包含两个维度：

- 最大模型差异：哪个环节在拉开差距。
- 能力边界：当前在这类任务上已经能做到什么、哪些还需要人纠正才能做对。

好的洞察示例〔原文小字，部分难辨〕：「多数模型能画出立体建筑、道路、车辆和行人的简洁〔?〕，但都没有按照同一套等距轴〔?〕；各模型在配色上的共同问题不是少元素，而是〔?〕装饰统一〔?〕」。

差的示例：「A 的视觉最好，C 漏了行人。」

【红字】不要照抄维度打分原文，必须说明好在哪里、差在哪里，不要直接粘贴 AI 的检查结果。按照评测作业流程，最后填写评测洞察部分，确保洞察是全面的。

## 8. 质检与修改反馈

### 8.1 质检职责与回避

质检员负责质检提交的评测结果、反馈质检意见，并更新 Coding Agent 人评质量记录表当期条目。同一人同时承担标注和质检时，两个角色分别统计、分别考评。

- 回避：质检员不得质检自己标注的样本。
- 盲评：盲评项目中，质检员不接触参评模型的真实身份，也不得打探或按照模型身份预判判定。

### 8.5 意见沟通

- **评价回复**：标注员看到表格评论后须回复，修改完成后也须回复；质检员同样须及时回复（包括在题目质检群）标注员的疑问。
